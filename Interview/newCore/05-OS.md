# Operating Systems (OS) — Interview Prep Guide

> Goal: Explain how the OS juggles processes, memory, and concurrency — and answer the perennial gotchas (process vs thread, deadlock, paging, semaphore vs mutex). OS questions reward crisp definitions plus a real example of *why the mechanism exists*.

---

## 0. How OS gets tested

- **Definitions + distinctions:** process vs thread, mutex vs semaphore, paging vs segmentation, deadlock vs starvation.
- **Scheduling problems:** "Given these processes and burst times, compute average waiting time for SJF / Round Robin."
- **Concurrency classics:** producer-consumer, readers-writers, dining philosophers.
- **Deadlock:** the four conditions, prevention vs avoidance vs detection.
- **Memory:** virtual memory, page faults, page-replacement algorithms, thrashing.

---

## 1. What an OS does (the framing)

The OS is a resource manager sitting between hardware and applications. Its four big jobs:
1. **Process management** — create, schedule, and terminate processes; enable multitasking.
2. **Memory management** — allocate memory, provide each process an isolated address space, manage virtual memory.
3. **File system management** — organize storage into files/directories, control access.
4. **I/O & device management** — mediate access to disks, network, keyboard via drivers.

**Kernel** = the core, always-in-memory part running in privileged mode. **User mode vs kernel mode:** user programs run in restricted user mode; to do privileged things (I/O, memory allocation) they make a **system call**, which traps into kernel mode. This protection boundary is why one crashing app doesn't take down the machine.

---

## 2. Process vs Thread (the #1 OS question)

**Process:** an independent program in execution, with its *own* address space (code, data, heap, stack), and OS resources (file handles). Isolated from other processes.

**Thread:** the smallest unit of execution *within* a process. Threads of the same process **share** code, data, heap, and open files — but each has its own **stack, registers, and program counter**.

| | Process | Thread |
|---|---|---|
| Memory | Separate address space | Shared within the process |
| Communication | IPC needed (pipes, sockets, shared memory) — expensive | Just shared memory — cheap, but needs synchronization |
| Creation cost | Heavy | Light |
| Crash isolation | One crash doesn't affect others | One thread crashing can bring down the whole process |
| Context switch | Expensive (swap address space) | Cheaper (same address space) |

**Real example to say:** "A browser uses *processes* per tab so one crashed tab doesn't kill the browser (isolation). Within a tab it uses *threads* — one for rendering, one for network, one for JS — because they need to share the page's data cheaply."

**What's shared vs private (favorite follow-up):**
- **Shared** among threads: code segment, data segment, heap, open files.
- **Private** per thread: stack, registers, program counter.

## 3. Process states & the PCB

**Process life cycle:**
```
NEW → READY → RUNNING → TERMINATED
        ↑        ↓
        └─── WAITING (blocked on I/O)
```
- **New:** being created. **Ready:** waiting for CPU. **Running:** executing. **Waiting/Blocked:** waiting for I/O or an event. **Terminated:** finished.

**PCB (Process Control Block):** the data structure the OS keeps per process — PID, process state, program counter, CPU registers, memory info (page tables), scheduling info (priority), open file list. On a **context switch**, the OS saves the running process's state into its PCB and loads the next process's state from its PCB. Context switches are pure overhead — no useful work happens during them.

**Zombie vs orphan process (gotcha):**
- **Zombie:** finished executing but its entry lingers in the process table because the parent hasn't read its exit status (`wait()`). Harmless individually but leaks table entries.
- **Orphan:** parent died first; the orphan is "adopted" by the init/systemd process, which reaps it.

## 4. CPU scheduling (expect a numeric problem)

The scheduler decides which ready process runs next. Goals: maximize CPU utilization & throughput; minimize waiting time, turnaround time, response time.

**Key metrics:**
- **Turnaround time** = completion time − arrival time.
- **Waiting time** = turnaround time − burst time.
- **Response time** = first-run time − arrival time.

### The algorithms
| Algorithm | Idea | Preemptive? | Downside |
|-----------|------|-------------|----------|
| **FCFS** | First come, first served (queue) | No | **Convoy effect** — one long job stalls everyone behind it |
| **SJF** | Shortest job first | No | Needs to know burst time; **starves** long jobs |
| **SRTF** | Shortest remaining time (preemptive SJF) | Yes | Same starvation risk |
| **Round Robin** | Each gets a fixed time quantum, then rotates | Yes | Performance depends heavily on quantum size |
| **Priority** | Highest priority runs first | Either | Starvation of low priority → fix with **aging** |
| **MLFQ** | Multiple queues, jobs move between them by behavior | Yes | Complex; used in real OSes |

**Round Robin quantum trade-off (common question):** Too large → behaves like FCFS. Too small → excessive context-switch overhead. Pick it a bit above typical burst time.

**Aging:** gradually raise a waiting process's priority so it eventually runs — prevents starvation in priority scheduling.

### Worked example — SJF
Processes (arrival 0): P1 burst 6, P2 burst 8, P3 burst 7, P4 burst 3.
SJF order by burst: **P4(3) → P1(6) → P3(7) → P2(8)**.
- Completion: P4=3, P1=9, P3=16, P2=24.
- Waiting = start time: P4=0, P1=3, P3=9, P2=16 → avg = (0+3+9+16)/4 = **7**.
Compare FCFS order P1→P2→P3→P4: waiting = (0+6+14+21)/4 = **10.25**. SJF minimizes average waiting time — that's its whole point.

## 5. Concurrency & synchronization (the meatiest topic)

When multiple threads touch shared data, you get bugs unless you coordinate.

### The core problem — race condition & critical section
- **Race condition:** the outcome depends on the *timing/interleaving* of threads. Classic: two threads both do `balance = balance + 100`. Read-modify-write isn't atomic, so one update can be lost.
- **Critical section:** the code region that accesses shared data. Only one thread should be inside at a time. Requirements for a solution: **mutual exclusion**, **progress**, **bounded waiting**.

### The tools
- **Mutex (lock):** a binary lock; one thread holds it, others wait. Has **ownership** — only the locker can unlock. Use to protect a critical section.
- **Semaphore:** a counter with `wait()` (P, decrement/block if 0) and `signal()` (V, increment). A **binary semaphore** (0/1) acts like a lock but has *no ownership*; a **counting semaphore** allows N concurrent holders (e.g., a pool of 5 DB connections).
- **Monitor / condition variable:** higher-level construct bundling mutual exclusion with the ability to wait for a condition (e.g., Java `synchronized` + `wait()`/`notify()`).

**Mutex vs Semaphore (guaranteed question):**
> "A mutex is a *locking* mechanism with ownership — the thread that locks must unlock, used for mutual exclusion over a resource. A binary semaphore is a *signaling* mechanism with no ownership — one thread can signal what another waits on, used for coordination between threads. A counting semaphore additionally lets up to N threads access a resource pool."

### Atomic operations & spinlocks
- **Atomic operation:** completes in a single indivisible step (e.g., compare-and-swap, CAS) — the hardware primitive underlying lock-free code.
- **Spinlock:** a lock that *busy-waits* (loops) instead of sleeping. Good when the wait is very short and sleeping's overhead would dominate; bad if held long (wastes CPU).

## 6. Deadlock (a whole section on its own — very common)

**Deadlock:** a set of processes are each waiting for a resource held by another — none can proceed. Ever.

**The four Coffman conditions (ALL must hold for deadlock):**
1. **Mutual exclusion** — resources can't be shared; held exclusively.
2. **Hold and wait** — a process holds one resource while waiting for another.
3. **No preemption** — resources can't be forcibly taken; only released voluntarily.
4. **Circular wait** — a cycle of processes each waiting for the next's resource.

Break *any one* → no deadlock. This is the framework for prevention.

**Handling strategies:**
- **Prevention:** design so one condition can't hold. E.g., break *circular wait* by imposing a global lock-ordering (always acquire locks in the same order). Break *hold-and-wait* by requiring all resources upfront.
- **Avoidance:** grant resources only if the system stays in a "safe state" — the **Banker's Algorithm** (know the name: it simulates allocation to check safety before granting).
- **Detection & recovery:** allow deadlocks, detect via a wait-for graph (cycle = deadlock), recover by killing/rolling back a process.
- **Ostrich algorithm:** ignore it and reboot if it happens (what most OSes practically do for rare cases — yes, this is a real term).

**Deadlock vs Starvation vs Livelock (distinction question):**
- **Deadlock:** processes stuck forever waiting on each other.
- **Starvation:** a process waits indefinitely because others keep getting preferred (e.g., low priority forever skipped). Fixed by aging.
- **Livelock:** processes keep *changing state* in response to each other but make no progress (two people stepping side-to-side in a hallway).

## 7. Classic synchronization problems (know the setup + the fix)

**Producer-Consumer (bounded buffer):** producers add to a fixed buffer, consumers remove. Need: don't add when full, don't remove when empty, no simultaneous access.
- Solution uses **3 semaphores:** `empty` (counts free slots, starts at N), `full` (counts filled slots, starts at 0), and a `mutex` for the buffer. Producer: `wait(empty); wait(mutex); add; signal(mutex); signal(full)`. Consumer mirrors it.

**Readers-Writers:** many readers can read simultaneously, but a writer needs exclusive access. Challenge: prevent writer starvation (or reader starvation, depending on the variant).

**Dining Philosophers:** 5 philosophers, 5 forks; each needs both neighboring forks to eat. Naive "grab left then right" → everyone grabs left → **deadlock** (circular wait!). Fixes: allow at most 4 to sit, or make one philosopher grab right-then-left (break symmetry / lock ordering), or use a waiter (arbitrator). This problem is literally a deadlock demonstration.

## 8. Memory management

### The address-space layout of a process
```
High addr  ┌──────────────┐
           │    Stack     │  ↓ grows down (local vars, function frames)
           │      ⋮       │
           │     Heap     │  ↑ grows up (dynamic: malloc/new)
           │ BSS / Data   │  global/static variables
Low addr   │ Text (code)  │  the program instructions
           └──────────────┘
```
**Stack vs Heap (extremely common):** Stack = automatic, LIFO, fast, function-scoped, size-limited (stack overflow); managed by the compiler. Heap = manual/GC'd, dynamic lifetime, larger, slower, can fragment; you (or the GC) manage it.

### Virtual memory — the key abstraction
Each process gets its own large, contiguous *virtual* address space, decoupled from physical RAM. The OS + MMU translate virtual → physical addresses. Benefits: **isolation** (processes can't touch each other's memory), **more memory than RAM** (spill to disk), **simpler programming** (no worrying about physical layout).

### Paging
Physical memory is split into fixed-size **frames**; virtual memory into equal-size **pages**. A **page table** maps virtual pages → physical frames. Advantage: no external fragmentation (any frame fits any page). The **TLB (Translation Lookaside Buffer)** caches recent translations so most lookups skip the page table.

**Page fault:** the referenced page isn't in RAM. The OS pauses the process, fetches the page from disk into a frame (possibly evicting another), updates the page table, and resumes. A *minor* fault = page is in memory but not mapped; a *major* fault = must read from disk (slow).

### Segmentation
Memory divided into variable-size logical **segments** (code, stack, data) matching the program's structure. Suffers **external fragmentation**. Modern systems often combine segmentation + paging.

**Internal vs external fragmentation:**
- **Internal:** wasted space *inside* an allocated block (fixed-size pages → the last page is partly empty). Paging's flaw.
- **External:** enough total free memory but scattered in small non-contiguous holes → can't satisfy a large request. Segmentation's flaw.

### Page-replacement algorithms (numeric questions appear)
When RAM is full and a new page is needed, which to evict?
- **FIFO:** evict the oldest-loaded page. Simple, but suffers **Belady's anomaly** (more frames can *increase* faults — counterintuitive, worth knowing the name).
- **LRU (Least Recently Used):** evict the page unused for the longest. Good approximation of optimal; costly to track exactly (use approximations like the clock/second-chance algorithm).
- **Optimal (OPT/MIN):** evict the page not needed for the longest future time. Theoretically best but requires knowing the future — used as a benchmark only.

**Thrashing:** the system spends more time swapping pages in/out than executing — happens when too many processes compete for too little RAM (high page-fault rate). The OS fixes it by reducing the degree of multiprogramming or using a **working-set model** to give each process enough frames.

## 9. IPC — Inter-Process Communication

Since processes have separate address spaces, they need explicit channels:
- **Pipes:** unidirectional byte stream between related processes (`ls | grep`). Named pipes (FIFOs) work between unrelated processes.
- **Shared memory:** a region mapped into multiple processes' address spaces — *fastest* (no copying) but needs synchronization.
- **Message passing / message queues:** send/receive discrete messages via the kernel.
- **Sockets:** communication across machines (or same machine) over the network stack.
- **Signals:** asynchronous notifications (e.g., `SIGKILL`, `SIGTERM`).

**Trade-off:** shared memory is fastest but you manage synchronization; message passing is slower (kernel-mediated copies) but simpler and safer.

---

## 10. File systems & storage (lighter, but asked)

- **File system:** organizes data into files/directories, tracks metadata (permissions, timestamps, size) and where blocks live on disk. Examples: ext4, NTFS, APFS.
- **Inode:** a structure holding a file's metadata and pointers to its data blocks (the filename is separate, in the directory).
- **Contiguous vs linked vs indexed allocation:** how a file's blocks are laid out — contiguous (fast, fragments), linked (no fragmentation, slow random access), indexed (an index block points to data blocks — the inode approach).

## 11. Rapid-fire concept questions

1. **Process vs thread one-liner?** Process = isolated program with its own memory; thread = lightweight unit inside a process sharing its memory.
2. **What is a context switch and why costly?** Saving one process/thread's state and loading another's; pure overhead, no useful work; worse for processes (address-space swap).
3. **Mutex vs semaphore?** Mutex = lock with ownership for mutual exclusion; semaphore = counter for signaling / limiting N concurrent accesses, no ownership.
4. **Four conditions for deadlock?** Mutual exclusion, hold-and-wait, no preemption, circular wait.
5. **What causes thrashing?** Too little RAM for too many active processes → constant paging, high page-fault rate, little real work.
6. **Paging vs segmentation?** Paging = fixed-size pages/frames (internal fragmentation); segmentation = variable logical segments (external fragmentation).
7. **What is virtual memory for?** Isolation, running programs larger than RAM, and giving each process a simple contiguous address space.
8. **Preemptive vs non-preemptive scheduling?** Preemptive can interrupt a running process (Round Robin, SRTF); non-preemptive runs to completion/block (FCFS, SJF).
9. **What is a system call?** The controlled entry point from user mode into kernel mode to request a privileged service (I/O, memory, process creation).
10. **Starvation vs deadlock?** Deadlock = permanent mutual waiting; starvation = one process indefinitely deprived while others proceed (fixed by aging).
11. **Zombie vs orphan?** Zombie = finished but not reaped by parent; orphan = parent died, adopted by init.
12. **Belady's anomaly?** In FIFO paging, adding more frames can increase page faults.

## 13. The 60-second summary

> "The OS manages processes, memory, concurrency, and I/O behind a user/kernel protection boundary. Processes are isolated with their own address spaces; threads live inside a process and share its memory cheaply but need synchronization. The scheduler multiplexes the CPU — FCFS, SJF, Round Robin, priority — trading off throughput, waiting time, and starvation, which aging fixes. Concurrency needs mutual exclusion over critical sections via mutexes and semaphores; get resource ordering wrong and you hit deadlock, which requires all four Coffman conditions and is handled by prevention, avoidance, or detection. Virtual memory via paging gives each process isolation and more space than RAM, backed by a page table and TLB, with page-replacement policies like LRU deciding evictions — and if you over-commit, the system thrashes."
